# デザイン原則

デザイントークン・視覚表現を追加・変更するときの判断基準を定義する。
Panda CSS の機械的な規則は [styling.md](./styling.md)、UI 命名は [design-system-terminology.md](./design-system-terminology.md)、コンポーネント責務と共通化基準は [components.md](./components.md) を正とし、本ファイルはそれらの上位にある設計判断を扱う。

出典: 姉妹リポジトリ Harp（Marp スライドのデザインシステム）の DESIGN.md から、ブログに適用可能な概念を抽出・翻案した。

## デザインコンセプト

本サイトは、読み手が本文と根拠を追うための画面である。
デザインは、情報の順序、視線の移動、重要度の差を明確にするために使う。
装飾は、内容の階層を読みやすくする範囲に抑える（Low ornament）。

## Adobe Spectrum との関係

`@adobe/spectrum-tokens` は値の供給源であり、Adobe の見た目に寄せるためのものではない（[tokens/colors.ts](../../src/ui/styled/theme/tokens/colors.ts)）。
採用理由は、読みやすさ、意味の一貫性、調整しやすさをデザイン判断の基準にするためである。

Spectrum の Inclusive design の前提は、本サイトでは次の形で扱う。

- **構造を先に整える**: 見出し、本文、図版、注記の読み順を崩さない。画面上の配置と DOM 順序を矛盾させない。
- **色だけで伝えない**: 状態や重要度は、色に加えてラベル、線、太さ、位置、形で示す。
- **読みやすさを優先する**: 本文は左揃えを基本にし、長すぎる行と詰まった行間を避ける。
- **代替情報を残す**: 画像・図版には意味のある alt を付け、説明に必要な情報は本文にも置く。
- **判断を文書化する**: アクセシビリティや表示上の判断は、token 定義、コンポーネント JSDoc、ルールのいずれかに残す。

## 🟡 トークン階層 (IMPORTANT)

デザイン値は次の 3 層で扱う。

| 層              | 場所                                     | 内容                                                              |
| --------------- | ---------------------------------------- | ----------------------------------------------------------------- |
| primitive       | `src/ui/styled/theme/tokens/`            | Spectrum 由来のパレットと基礎スケール（gray、spacing、fontSizes） |
| semantic        | `src/ui/styled/theme/semanticTokens/`    | サイト全体の役割（bodyBackground、focusRing など）                |
| component-local | 各コンポーネント内の CSS custom property | その部品内でしか使わない座標・寸法・派生値                        |

semantic token は増やしすぎない。次のいずれかを満たす値だけを semantic token にする。

- 複数箇所を同じ判断で動かす値である（例: 反転面の背景を一括で変える）。
- サイト全体の役割を表す値である（例: ページ背景、フォーカスリング）。

一度しか使わない値は共通トークンにせず、利用箇所でパレットを直接参照するか、component-local な CSS custom property に閉じる。
semantic token の定義には、名前だけで利用箇所が読み取れない場合に限り、1 行コメントで役割を補足する（実際の利用箇所を確認できるものだけに付ける）。

## 🔴 色の運用 (CRITICAL)

色は、色相の多さではなく意味の差で使い分ける。

- 基本はニュートラルなグレー（`gray-*` / `grayA-*`）を使う。`accent-*` は同じグレーの濃度別名（1100 以降は black）で、フォーカスとホバーの強調に使う。色相では強調しない。
- 状態色（green / red / yellow / purple など）は、Alert のように意味が定義された部品に限る。
- **単発の強調色を追加しない**。1 箇所だけの装飾のために新しい色相を持ち込まない。
- 新しい色の役割を追加する場合は、色名ではなく役割名で命名する（`blueBox` ではなく `notePanel`）。追加時にコントラスト、非カラー情報での代替、ダークテーマへの耐性を確認する。

パレット直接参照（`var(--colors-gray-900)` など）は禁止しないが、次のスケール数値の用途目安に従う。

- 25-100: 地と面
- 200-500: 帯・チャートの棒などの濃い面、無効状態
- 600-800: 副の文字、テキスト以外の静的な装飾
- 900 以上: 主の文字色・アイコン・状態色

この区分は Spectrum の規定ではなく、本リポジトリの運用実態に基づく整理である。

文字色は、載る面に対して 4.5:1 以上になる段から選ぶ。既定は主 gray-900・副 gray-700（日付・件数・補足）である。gray-600 は、載る面で 4.5:1 を確かめてから使う。次の表の面は、ブラウザで実測した描画の色（地の gray-50 に黒の層を重ねた色）で、比は WCAG 2.2 の式で計算した値である。ページ上部の帯は黒 9% の三角形 2 枚で描かれ、重なる所は 2 枚分になる。

| 載る面                            | gray-600 | gray-700 |
| --------------------------------- | -------- | -------- |
| 白（gray-25）                     | 4.88     | 8.06     |
| 地（gray-50）                     | 4.60     | 7.59     |
| フッター（gray-75）               | 4.40     | 7.27     |
| hover の面（黒 5%）               | 4.13     | 6.83     |
| タグの面、帯 1 枚（黒 9%）        | 3.77     | 6.22     |
| タグの hover、current（黒 12%）   | 3.49     | 5.77     |
| 帯 2 枚の重なり（黒 9% を 2 枚）  | 3.07     | 5.07     |
| current の面が帯 2 枚の上に載る所 | 2.35     | 3.89     |

gray-600 が 4.5:1 に届くのは、白と地の上だけである。gray-500 以下は地の上でも届かない（3.05:1）。base CSS などに残る gray-1000 の文字色は未移行であり、新規・変更コードでは踏襲しない。

インタラクティブ状態（hover / focus / active）の色は、色相を変えず濃度で差を付ける。

- **フォーカス表示**: `:focus-visible` の標準表示は semantic token の `focusRing`（`accent-900` = gray-900）に任せる。コンポーネントごとに独自のフォーカス色を定義しない。
- **hover / active の強調**: 既定は `gray-1000`。hover はより濃いインク（`accent-1100` = black）へ上げる。切り替え色は部品ごとの判断として component-local な CSS custom property に閉じる（例: ArticleCard は `--hover-color: var(--colors-accent-1100)` を定義し、既定のテキスト `gray-1000` と枠線 `gray-200` を hover で切り替える。active は色を変えず線幅で差を付ける）。

`focusRing` の `accent-900`（gray-900）と ArticleCard の `accent-1100`（black）が異なるのは層の違いによる。focusRing はサイト全体を一括で動かす固定役割、hover 色は部品内に閉じた判断であり、値を無理に統一しない。テキストの色は、載る面で 4.5:1 以上になる段から選ぶ（既定は主 gray-900・副 gray-700）。current の面が帯の重なる所に載ると、副の gray-700 でも 3.89:1 になり 4.5:1 を下回るので、その面に副を置かない。

同じ意図の色参照が複数箇所に散り始めたら、semantic token への昇格を検討する。閾値の考え方は [components.md](./components.md) の共通化基準に合わせる。

## 🟡 余白の運用 (IMPORTANT)

余白は Spectrum spacing スケール（`--spacing-50`〜`--spacing-1000`、2〜96px の 12 段）を唯一の尺度とする。
値は `@adobe/spectrum-tokens` から抽出し、期待 px 値と照合してから公開する（[tokens/spacing.ts](../../src/ui/styled/theme/tokens/spacing.ts)。パッケージ更新による暗黙のスケール変動を codegen 時に検知するため）。primitive 12 段は長期固定の契約として扱う。

- layout primitive の gap API（`SpaceGap`）は、サイトのリズムを構成する subset（75 / 100 / 300 / 400 / 500 / 600 / 700 / 800 / 1000）に制限する。段を増やす場合は実際の利用箇所を提示する（500 は格子・タグの一覧の見出しと内容の間隔 row で、PostSection の card と TagSection が使う。700 は見出しと行の並びの間隔 title（ページ見出しと同じ値）で、PostSection の timeline と年ごとの区切りが使う）。
- 600 以降の隣接段は比が 1.2〜1.33 倍で知覚差が小さい。段は役割（title / page / section など。base CSS の `--spacing-*`）ごとに 1 つ割り当て、画面幅で同じ役割を広げる切り替えは隣接段でよい（page 700→800）。title は幅で広げない（48）。最も大きな区切りの section は段飛ばし（800→1000）にする。
- スケールにない寸法を calc() の合成で作らない。オフセットや反転（`* -1` など）の算術は許容する。

## 線と面

- 影と枠線は使わない。線はフォーカス枠とリンクの下線に限る（リデザイン引き継ぎ資料の tokens/colors.css 原則 1）。
- 面（`grayA-75` の fill、フッターの `gray-75` など）は背景から情報単位を分けるために使い、選択状態（current）は面で示す（太字にしない）。
- 階層を作るときは、余白と面で分ける。既存コードに残る枠線・影（ArticleCard の枠線、base CSS の pre・table の罫線など）は未移行であり、新規・変更コードでは踏襲しない。
- カードの中に装飾カードを重ねて階層を作らない。

## 拡張判断

新しいデザイン要素（色役割、装飾、視覚部品）を追加する前に、次を確認する。

- その要素は内容の階層を明確にするか。装飾のための装飾になっていないか。
- 既存のトークン、layout primitive、コンポーネントで表せないか。
- 1 回限りの表現か、今後も使う表現か。
- 色だけに依存せず、形、線、位置、ラベルでも意味が伝わるか。
- 読み順、代替情報、コントラスト、文字量に問題がないか。

## 適用しない Harp 概念

出典の Harp は Marp スライド（固定キャンバス・発表資料）であり、前提が違う次の規則は本リポジトリに適用しない。

| Harp の規則                    | 適用しない理由                                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| BEM 命名                       | class は Panda CSS の生成物である。命名は [design-system-terminology.md](./design-system-terminology.md) を正とする |
| アニメーションの原則禁止       | 本サイトは動きを設計要素として使う。点滅・長く続く動き・注意を奪う動きを避ける方針は共有する                        |
| 固定キャンバス前提の文字量削減 | Web はスクロールとリフローを前提にする。行長制限と階層設計で読みやすさを担保する                                    |
