# ドキュメント執筆ガイドライン

このリポジトリの Markdown 文書を新しく書くとき、直すときの規則である。確かめた事実だけを、初見の読者に通じる言葉と順序で書くことを求める。

## 適用範囲

- 対象は、README.md、CONTEXT.md、`docs/`、`tests/vrt/README.md` など、人間と AI が読む Markdown 文書である
- 文書の種類ごとの定めがある場合は、その定めを優先する
  - `_article/` の記事は、別リポジトリの submodule にある。このリポジトリからは編集せず、参照先のリポジトリで直す（[content-pipeline.md](../architecture/content-pipeline.md)）
  - `.claude/skills/` と `.claude/agents/` の定義ファイルは、それぞれの形式に従う
  - `.github/copilot-instructions.md` は、`CLAUDE.md` と `AGENTS.md`（どちらもこのファイルへのシンボリックリンク）の実体である。編集は実体に行う。`<!-- BEGIN:nextjs-agent-rules -->` と `<!-- END:nextjs-agent-rules -->` の間は `next dev` が書き込むため、手で直さない
  - 規則の本文は、内容の種類に合う `docs/` のディレクトリ（一覧は [docs/README.md](../README.md)）の文書に書く。1 つの文書には 1 つの主題を書き、規則から文書単位で指せるようにする。`.claude/rules/` には、規則の本文を書かない
    - `.claude/rules/` の規則は、作業の種類（コンポーネント、スタイル、テストなど）ごとに 1 ファイルにする。frontmatter の `paths` に、その作業で触れるファイルの glob を書き、本文に、その作業で読む `docs/` の文書へのリンクを、読む場面を添えて並べる。1 つの文書を、複数の規則から指してよい
    - リンク先は自動では読み込まれず、Claude が `Read` で読む。文書を足したら、その文書を読む作業の規則にリンクを足す。どの規則からも指されない文書は、規則の案内では読まれない
    - 作業するファイルによらず必要な文書だけは、`.claude/rules/always.md` に `@` で取り込む。この規則に `paths` は書かない
    - Claude Code が規則から読む項目は `paths` だけである。`paths` を書かない規則は、起動時に毎回読み込まれる
    - `@` は、`paths` を付けた規則に書かない。`paths` があっても、取り込み先は起動時に読み込まれ、`paths` で絞れない（2026-11-16 は Claude Code 2.1.325、2026-11-21 は 2.1.330 で、`InstructionsLoaded` フックのログで確認した。公式ドキュメントの `paths` の節に、`@` の取り込み先についての記述は無い）
    - `docs/` の文書には `paths` を書かない。`.claude/rules/` の外にある文書の `paths` は、Claude Code に読まれない（2026-11-21、2.1.330 で確認した）
    - 取り込む文書が増えるほど、読み込む文脈が大きくなる。毎回読み込む分（`CLAUDE.md`、`.claude/rules/always.md`、その取り込み先）は、合わせて 200 行以内にする。公式ドキュメントの「1 ファイル 200 行以内」の目安を、毎回入る分の合計に当てた自主上限で、`wc -l` で数える
    - 書き方は [Claude Code の公式ドキュメント](https://code.claude.com/docs/en/memory#path-specific-rules)に従う
- 言語と文体は、[`.github/copilot-instructions.md`](../../.github/copilot-instructions.md) の「プロジェクト」節にある「言語」に従う。README.md と SECURITY.md は英語で書かれており、この 2 つを直すときは英語のまま直す
- 既存の文書に、このガイドラインに沿わない箇所や、現在のコード・設定と食い違う記述があっても、依頼がなければ書き換えない。直すのは、依頼された範囲と、その変更で内容が合わなくなる箇所（要約・一覧・リンク）に限る。ほかに気づいた点は依頼者に伝える

## 実在と挙動は確認してから書く

- 次のものは、実在を確かめてから書く
  - パス・ファイル名: `ls` で確かめる
  - 関数名・コンポーネント名・型名: `rg` で探す。近い名前の別のものと取り違えない
  - コマンド: `package.json` の `scripts` などの定義で確かめる
  - リンク: リンク元のファイルの位置から、相対パスを辿って確かめる。ただし `.github/copilot-instructions.md` のリンクは、リポジトリ直下を基準に書かれている（`.github/` を基準にすると辿れない）。URL は推測で書かない
- `rg` は既定では隠しディレクトリを検索しない。規則へのリンクとスキルは `.claude/` に、AI への指示は `.github/` にあり、`_article/` には記事が入っている。そのため `rg --hidden --glob '!.git' --glob '!_article' '<語>' .` の形で実行し、隠しディレクトリを含め、記事を除く。末尾の `.` は省かない。標準入力が端末でなく、パスも無い場合、`rg` はリポジトリではなく標準入力を検索し、0 件で終わるか入力を待ち続ける
- 挙動の説明は、該当するコード・設定を読んでから書く。名前や記憶から推測しない。確かめられなかった点は「未確認」と明記する。設定値は、[config-files.md](../tooling/config-files.md) が挙げる設定ファイルを読んで確かめる
- 既存の文書にある記述（パス・手順・数値）を引用・転記するときは、現在のコード・設定で確かめ直す
- 「唯一」「すべて」「必ず」「〜だけ」「〜は無い」と書くときは、根拠（コード・設定・一覧）と突き合わせて確かめる。確かめた結果のとおりに書き、確かめないまま「多くの」「基本的に」へ弱めない
- 数値（件数・版・所要時間など）を書くときは、対象・時点・求め方を添える。差や割合は、何と比べたかも書く
- 例に載せる値は、実際の認証情報・ID・個人情報ではなく、ダミーにする。`.env` の値や、Google Analytics・Webmention の応答を写すときは、すべての値をダミーに置き換える。README.md の `.env` の例が、ダミーの書き方の見本になる
- コミット時の `secretlint`（`package.json` の `nano-staged`）が検出するのは、`.secretlintrc.json` の規則に当たる形式だけである。検査を通ったことを、実値を書いてよい根拠にしない

## 初見の読者だけで理解できるようにする

- 読者は、ほかの文書・PR・Issue・会話を読んでいない前提で書く。その文書だけで意味が通るようにする
- 経緯を知らないと通じない表現（「以前の指摘を受けて」「今回の修正で」「新しい方式」）を書かない。いまの状態を、対象の名前を使って書く

## 用語は自分で作らず、具体語で書く

- 説明のための呼び名・略称を即席で作らない（「2 本立て」「例の対応」など）。書き手にしか通じない。すでにある名前で書く。コードの要素はコード上の識別子で、ライブラリや仕様は公式の表記で書く
- ドメインの語（Post、RawPost、PostSummary、Tag、Slug、Source など）は、[CONTEXT.md](../../CONTEXT.md) の定義のとおりに書く。名前から意味を推測しない。たとえば `TagCounts.slug` は、URL-safe な slug ではなく、Tag の表示名である
- UI の語（Inner、Container、Gap、Gutter、Section など）は、[terminology.md](../design-system/terminology.md) の正式名称で書く。既存の API 名を説明するときは、同ファイルの「既存語の扱い」に従い、責務名を併記する
- 上の 2 つの文書と公式ドキュメントのどちらにも無い呼び名・略語（このリポジトリの中でだけ通じる通称など）は、初出で何を指すかを 1 文で書く。ほかの文書へのリンクは補足にとどめ、定義の代わりにしない
- 抽象名詞だけで文を組み立てない（「整合性に課題がある」）。何がどうなるのかを具体語で書く（「一覧の件数と詳細の件数が一致しない」）

## 例外・前提・未確認事項は削らない

- 規則や手順に付く例外・適用範囲・前提条件・未確認事項は、改稿や要約で落とさない。直したあとに `git diff` で消えた行を読み、落としていないかを確かめる
- 長くて本題が埋もれる場合は、削らずに移す。本文に要点を 1〜2 文で残し、詳細は別の節か別の文書に置いてリンクする

## 説明の一貫性を保つ

- 同じ役割の章・文書は、同じ見出し構成にする。同じ内容は 1 か所に書き、ほかの箇所からはリンクする
- 本文を直したら、同じ内容を要約している箇所も直す。対象には次がある
  - 文書内の概要
  - [`.github/copilot-instructions.md`](../../.github/copilot-instructions.md) の「クリティカルルール」の表
  - 規則文書に付けた「参照」の節
  - 適用対象を変えたときの、`.claude/rules/` のファイルの `paths`
- 同じ内容が複数の文書に書かれている場合は、`rg` で探して、正となるコード・設定と照合してそろえる。たとえば prebuild の流れは、`build/prebuild.sh` を正として、README.md、CONTEXT.md、[content-pipeline.md](../architecture/content-pipeline.md) に書かれている
- 文書や見出しを改名・移動・削除したら、そこへのリンクを `rg` で探して直す（見出しへのリンクは `#見出し名` の形）。`#` 以下は見出しの文字列から作られるため、見出し先頭の絵文字や末尾の `(CRITICAL)` を付け外すと、リンクが切れる。たとえば `layout.md#-zero-margin-principle-critical` の先頭の `-` は、見出しが絵文字で始まるために付く
- 用語や表記を変えると決めたら、変える範囲の全ての出現箇所を直し、旧表記が残っていないことを `rg` で確かめる

## 章の順番と、各章に書くこと

- 作業した順（時系列）ではなく、全体から詳細の順に並べる。読者が実行する手順は、実行する順に並べる
- 概要や結論の章には、いまどうなっているか・何を決めたかと、その理由だけを置く。根拠の内訳や細かい条件は、後ろの章に置く
- 経緯を書く場合は、その最後に、何が採用され、いまどうなっているかを書く。試行錯誤の細部は書かず、PR・Issue へのリンクにする
- 採らなかった案は、採用した形の理解に要るものだけを書く。ほかは PR・Issue へのリンクにする

## 表は 1 列 1 軸で作る

- 1 つの列には 1 つの軸（比べる観点）だけを書く。2 つの値を「A → B」のように 1 つのセルへ入れたり、「採用」「変更前」のような状態を内容の列へ書き足したりせず、列を分ける
- 表の列幅のそろえは、コミット時に prettier（`package.json` の `nano-staged`）が行う。手で合わせない
